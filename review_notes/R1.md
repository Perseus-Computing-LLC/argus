## Role mapping (cut vocabulary -> this repository)

- **Lease / lock holder (ledger).** There is no persistent lease. Each call takes an `fcntl.flock` on its own file description: `append()` takes LOCK_EX (src/argus_ledger/ledger.py:136-137) and releases it at ledger.py:205. `head()` (ledger.py:211-212), `_iter_records()` (ledger.py:260-261, released at 278) and the verifier's reader (ledger.py:285-286) take LOCK_SH.
- **Fencing token (ledger).** The tail record's `sequence` and `event_hash`, plus the monotonic timestamp floor. `append()` re-reads all three from the file under LOCK_EX on every call (ledger.py:138-162), so a writer has no cached head to go stale. Event hash v2 length-prefixes sequence, event_id, timestamp, type, actor, prev_hash and the payload digest (hasher.py:79-88). Signatures cover a domain tag plus the event hash (hasher.py:111-113), so without the key a signed record cannot be moved to another position or re-labelled v1.
- **Read-only holder.** A `verify_key` ledger refuses to append (ledger.py:130-131). This holds.
- **Authority / redemption token.** `PraxaGovernanceGovernor.current_token` (src/argus_ledger/proofweave.py:309, 320-324, 333-337) is the only fencing token in the literal sense: it gates `execute_with_broker()`. `PolicyActionBinding.redemption_token` (proofweave.py:33, 50) is described as a "One-time grant token". `proofweave` is exported from the package (`__init__.py`). README.md:105 calls it "experimental (API may change)"; that is a stability caveat, and it does not document the behaviours below as intended. The class docstring promises "non-bypassable lifecycle transitions" (proofweave.py:299-303) and `evaluate_proposal` promises "a single-use authority token" (proofweave.py:313).

### Checked by reading, holding

- Concurrent appenders: sequence, prev_hash and the timestamp floor are taken from the file under LOCK_EX, so two holders cannot both extend the same head (ledger.py:136-162).
- v2 signatures cannot be replayed as v1 signatures, because of domain separation at hasher.py:111-113.
- The v1 colon-join ambiguity is documented as a known legacy property (hasher.py:9-11). Not reported.

## Findings (each proven by a test that exits 1 on head)

1. **high**: `tests/review1_praxa_token_unbound_action.py` (exit on head = 1)
   - The authority token is not bound to the action it authorized.
   - `evaluate_proposal()` checks only `intent["action"]` against `prohibited_actions` (proofweave.py:314-318). It derives the token from the intent hash (proofweave.py:320-322) but stores nothing about which intent it approved.
   - `execute_with_broker()` compares only state and token (proofweave.py:333-334), then passes the caller's arbitrary `action` to `broker_fn` (proofweave.py:338).
   - So a token issued for `{"action": "read_report"}` runs `{"action": "drop_database"}`, which the policy prohibits. This is the cut's laundering case exactly: a valid token for X fences in Y.
   - Rated high because it breaks the governor's only fencing guarantee.

2. **medium**: `tests/review1_praxa_token_replay.py` (exit on head = 1)
   - The "single-use" token is deterministic: `sha256("PRAXA_AUTH:<intent hash>:<policy hash>")[:32]` (proofweave.py:321-322), and `policy_hash` is a public attribute (proofweave.py:307).
   - Clearing the token after use (proofweave.py:337) makes it single-use within one cycle only. Re-authorizing the same intent re-issues the identical value, so a token consumed in an earlier cycle (or computed by anyone who knows intent and policy, without ever being issued one) is accepted in the next authorization window.
   - The fix needs an unpredictable per-issuance token.

3. **medium**: `tests/review1_praxa_failed_broker_verified.py` (exit on head = 1)
   - `execute_with_broker()` sets `state = EXECUTED` and burns the token before calling the broker (proofweave.py:336-338), and nothing rolls back if `broker_fn` raises.
   - `verify_effect()` gates only on `state == EXECUTED` (proofweave.py:349-350). It therefore seals a `ProofWeaveTransaction`, appends it to `verified_transactions` and reports VERIFIED (proofweave.py:353-361) for a step whose execution failed, even with an honest readback that reports "not deployed".

4. **medium**: `tests/review1_praxa_verify_effect_launders_intent.py` (exit on head = 1)
   - `verify_effect()` takes `intent` and `action` from the caller (proofweave.py:341-347) and binds them with the governor's policy (proofweave.py:353-359). Since the governor keeps no record of the authorized intent, it cannot compare.
   - After authorizing and executing `read_report`, the caller obtains a sealed VERIFIED transaction whose `intent_digest` is that of the prohibited `drop_database`, under the policy that forbids it. That is forged evidence of a policy-authorized forbidden action.
   - It shares a root cause with finding 1 (no stored authorized intent) but is a separate missing check at a separate call site. Fixing `execute_with_broker` alone does not fix it.

5. **medium**: `tests/review1_append_recreated_ledger_mode.py` (exit on head = 1)
   - The constructor creates the file 0600 (ledger.py:109-111) and documents "created owner-only (0600)" (ledger.py:88). The README (README.md:20) states the Python package writes its file "with `0600` permissions".
   - `append()` reopens by path with `open(path, "a+")` (ledger.py:136), so a handle that outlives its file recreates it with `0666 & ~umask` (0644 under umask 022). This happens when the file is rotated or moved aside while the writer runs, i.e. a stale holder. The audit payload of the next record then becomes readable by group and others.
   - The Rust writer creates with `mode(0o600)` on every append path (src/file_ledger.rs:239-241, 377-379) and repairs modes on open (file_ledger.rs:71-84).
   - Rated medium rather than high because it needs an external rotation or removal. It is adjacent to the cut: a stale handle writing to a path whose file changed.

6. **low**: `tests/review1_append_extends_malformed_tail.py` (exit on head = 1)
   - The writer's corrupted-tail gate only requires that `sequence` and `event_hash` are readable from `json.loads(tail)` (ledger.py:147-156).
   - A tail missing `timestamp` passes the gate. `timestamp_nanos("")` returns None (timestamps.py:29-38), which silently drops the monotonic floor at ledger.py:162.
   - `head()` rejects the same line (ledger.py:217-222), `verify_chain()` reports it broken at sequence 2, and the Rust writer parses the tail with `AuditEvent::from_json_line` and refuses (file_ledger.rs:254, 391).
   - A signing writer therefore extends and signs onto a head that its own reader rejects. The ledger stays tamper-evident (the break is still reported), hence low.

7. **low**: `tests/review1_iter_events_blocks_append.py` (exit on head = 1)
   - A suspended `iter_events()` generator (ledger.py:329-335) keeps `_iter_records()`'s LOCK_SH (ledger.py:260-261) until it is exhausted or closed (ledger.py:278).
   - `append()` opens a new description and blocks on LOCK_EX (ledger.py:136-137). flock locks on different descriptions conflict within one process, so `for ev in ledger.iter_events(): ledger.append(...)` deadlocks silently.
   - The test runs it in a subprocess with an 8 s timeout. It is a lock holder that never releases: a blocked write, not a forbidden one. Adjacent to the cut, hence low.

## Suspected, unconfirmed (no test file)

- `PolicyActionBinding.redemption_token` ("One-time grant token if ALLOW", proofweave.py:33) is a deterministic digest of the intent, policy and evidence hashes (proofweave.py:50), and the equality check at proofweave.py:78 relies on it being recomputable. Identical decisions get identical tokens, and the package has no redemption API, so "one-time" cannot be enforced or demonstrated here. Bearer-style use by a consumer would be replayable.
- `verify_effect()` never evaluates `readback_fn`'s result (proofweave.py:352-361). A readback that reports failure still produces VERIFIED. This may be intended (the readback is recorded as evidence for later audit), so not filed.
- `evaluate_proposal()` has no state guard (proofweave.py:312-324). Calling it while EXECUTED re-arms the governor, so the executed step can never be verified. A REJECTED governor can also be re-authorized. It is unclear whether REJECTED or EXECUTED are meant to be terminal.
- The caller-supplied `event_id` (ledger.py:127-129) is neither validated nor checked for uniqueness, although models.py:18 describes it as "Unique event ID (UUID/ULID)". The Rust writers never take a caller id: they derive it from a random per-instance `ledger_id` and the sequence (lib.rs:735-737, file_ledger.rs:293, 406). A replayed `event_id` lets a writer shadow an earlier event for consumers that index by id. Not filed: SECURITY.md Scope lists what verification checks (sequence, links, hashes, signatures), and uniqueness is not among them.
- After rotation, a live handle also silently starts a new genesis chain at the path (ledger.py:143-145). This is inherent to a file-state ledger and, per Scope, is detected by an out-of-band anchor. Noted only because it accompanies finding 5.
