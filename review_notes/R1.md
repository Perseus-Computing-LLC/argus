## The write path under review

The only state-changing surface in the package is `AppendOnlyLedger.append()` (src/argus_ledger/ledger.py:437-545) and the helpers it reaches:

1. `_open_locked_for_append()` (ledger.py:392-435): open-or-create (ledger.py:406, 410-412), `flock(LOCK_EX)` (ledger.py:417), inode identity check (ledger.py:418-423), `_restrict_to_owner` (ledger.py:424, 128-142), and the directory flush after creation (ledger.py:425-426, `_fsync_directory` at 77-83; `_make_directories` at 86-98 for missing parents).
2. The tail gate and torn-tail repair inside the lock: `_unterminated_tail` (ledger.py:61-74), `_tail_record` (ledger.py:45-58), `_is_record` (ledger.py:300-305), `_set_aside_torn_tail` (ledger.py:547-584: sidecar open 557, write 561, fsync 562, close 564, dir fsync 565, ftruncate 572, fsync 573).
3. The record write (ledger.py:530-535): one `os.write` loop under O_APPEND, then `os.fsync(fd)`; on any `BaseException` the rollback `_restore_length` (ledger.py:308-324) truncates back to the pre-append length and re-raises.

`proofweave.py` holds no syscalls (in-memory digests appended through `append()`); the native extension is read-only.

## Method

- **Kill sweep** (`scratch_probe/sweep.py` + `scratch_probe/child_kill.py`, output `scratch_probe/sweep.out`): a child process patches the mutating syscalls (`os.open`, `os.write`, `os.fsync`, `os.ftruncate`, `os.fchmod`) and `os._exit(9)` instead of making the Nth one — a real kill with no cleanup of any kind. 52 kill points across four scenarios (fresh ledger; second append onto one record; repair of a hand-crashed torn tail, unsigned and HMAC-signed), covering every mutating-syscall boundary of the path including all six of the repair (sidecar open → sidecar write → sidecar fsync → dir fsync → ftruncate → ledger fsync → record write → record fsync). The parent then inspected the state with the library's own API and checked, per kill point: C1 `verify_chain()` valid ⟹ the file ends with a complete record (a verifier must never accept a torn state); C2 `head()`/`iter_events()`/`verify_chain()` agree on tail parseability; C3 one unpatched recovery append leaves a valid, contiguous 1..k chain or fails without changing the file; C4 the acknowledged record survives byte-identical; C5 a removed fragment is preserved whole in a sidecar.
- **EIO-once sweep** (`scratch_probe/eio_sweep.py`): each mutating syscall made to raise `OSError(EIO)` once at each position, for a normal append and for the repair path, checking the "a reported failure leaves no record behind" rollback (ledger.py:536-541), recovery, and sidecar preservation.
- Directed probing of the remaining suspect: the durability flushes tied to file/directory creation (`scratch_probe/child_dirflush.py`).

## What held (verified, no finding)

- Every kill point in the record write, the fsync, the torn-tail repair and the sidecar path leaves exactly the two expected on-disk states: a clean prefix, or a clean prefix plus a fragment after the last newline. The next append repairs the fragment via the sidecar and chains correctly; `verify_chain()` never accepted a torn state; readers agreed; nothing before the last newline was ever removed; removed fragments were preserved whole in a sidecar (C1-C5 all green, 52/52 kill points and 13/13 EIO points).
- A kill between a completed `os.write` and the `os.fsync` leaves a complete, verifiable record that the caller never saw acknowledged (at-least-once; the retry appends sequence N+1, not a duplicate sequence). Inherent to any fsync-before-ack writer and consistent with ledger.py:537-539.
- A failed write or fsync is cut back to the pre-append length under the lock (`_restore_length`, ledger.py:540); a failure inside the repair leaves the fragment in place, fail-closed ("if the sidecar cannot be written, nothing is removed", ledger.py:566-570). These pin the R3-4/R3-9/R3-19 fixes.
- Self-bricking hunt: `validate_payload` (canonical.py:129-143) refuses every payload I could construct whose stored line `_parse_record` would reject (lone surrogates fail the canonical-bytes size check at canonical.py:142 with `UnicodeEncodeError`; integers, floats, depth, key types and size are gated); a payload that passes the gate but not the parse could not be constructed, so no "successful append bricks the ledger" path exists on this head.

## Findings (each proven by a test that exits 1 on head)

1. **medium**: `tests/review1_dir_entry_flush_lost_after_interrupted_create.py` (exit on head = 1; 3 failed assertions, 2 passing controls)
   - The flush that makes a new ledger file's *name* survive a crash is tied to the call that created the file, not to the file. `created` is a per-call local (ledger.py:403) set only by this call's `os.open(..., O_CREAT | O_EXCL, 0o600)` (ledger.py:410-412), and the flush runs only under `if created:` (ledger.py:425-426). The window between the create and the flush contains `fcntl.flock(LOCK_EX)` (ledger.py:417) — which can block arbitrarily long behind another writer — plus the inode check and `_restrict_to_owner`.
   - A writer killed in that window (the cut's exact scenario: a kill between two syscalls of the write path) leaves the file on disk with its directory entry never flushed, and no caller was ever told anything. Every later append takes the plain-open path (ledger.py:406), so `created` is False and the flush is skipped for ever: those appends fsync their records (ledger.py:535) and return success. The same state is reached without a kill by a single transient `EIO` on the directory fsync — the append fails, and the retry skips the flush because the file now exists. A second writer racing the killed one is in the same position: its `os.open` succeeds on the file the killed writer created, so it never flushes either.
   - One level up, `_make_directories` (ledger.py:86-98) has the same shape: it rebuilds its `created` list from `os.path.isdir` on every call (ledger.py:90), so directories that exist after an interrupted append are never flushed again. A later append flushes only the ledger's immediate directory (ledger.py:425-426), not the parents of the tree the killed writer created — so even that flush is moot: the ledger file's name is durable only if the entries of every directory above it are, and those were never flushed.
   - Consequence: ledger.py:397-398 names the hazard itself ("without that a crash can lose the new file's name while its records were fsynced") and README.md:95 promises the flush ("the first append creates the file (and missing directories) and flushes the directory entry"). In the state the test builds, every acknowledged record of the ledger can be lost to a crash while `append()` keeps succeeding, and no API reports or repairs the hole. This is the R3-12 fix (tests/rv1110_new_ledger_dir_not_fsynced.py) holding only on the happy path.
   - Rated medium rather than high: the kill alone loses nothing (the file is empty or absent at that instant); the loss needs a later power loss, and the window is one append. Rated medium rather than low because the miss is silent and permanent, the window includes an unbounded lock wait (a watchdog/OOM kill there is realistic), and the entire audit trail — not one record — is what becomes non-durable.

## Suspected, unconfirmed (no test)

- Rust-side parity of this finding: R3-12's notes establish that `src/file_ledger.rs` had no directory sync at all when reviewed; this round cannot build the Rust crate (per the brief), so whether the Rust `FileLedger` now flushes a created ledger's directory entry — and whether it re-flushes after an interrupted create — is unverified. The same per-call-flags shape would have the same hole.
- `_PrefixReader`'s docstring invariant (ledger.py:146-149: "those bytes never change once a snapshot has taken ``size``") is false during a torn-tail repair: `_set_aside_torn_tail`'s `ftruncate` (ledger.py:572) plus the subsequent append rewrite bytes *inside* a previously snapshotted prefix, so a suspended `iter_events()` that snapshotted while a fragment was present can, on resumption, yield a record appended after its snapshot (violating ledger.py:636's "Records appended after the snapshot are not yielded") or a prefix of the repairing record. I could not construct an observable harm distinct from the corruption error the reader already owes on the fragment it snapshotted, so no finding.
- `_set_aside_torn_tail` (ledger.py:571-578): if the `ftruncate` succeeds but the `os.fsync` after it fails, the `LedgerCorruptionError` says the fragment "could not be removed ... the tail needs recovery" while in page-cache truth it is gone. Defensible as "not removed durably" (after a power loss the truncate may not persist), and the next append heals either way, so not filed.
- Debris: a kill during the sidecar write (between ledger.py:557 and 562) leaves a partial sidecar file whose name is indistinguishable from a complete one and which nothing ever cleans; a kill between the sidecar flush and the `ftruncate` leaves the same fragment saved twice under two names. Cosmetic.
