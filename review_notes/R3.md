## Restatement (restate gate, written before reading code in depth)

1. Round 3 reviews the Argus ledger (Python `src/argus_ledger/*`, Rust `src/lib.rs`, `src/file_ledger.rs`, `src/bin/argus_verify.rs`) on a new cut: (a) durability and crash consistency of the file ledger, (b) agreement between the Python verifier, the Rust verifier and the Python streaming/non-streaming paths, (c) verification that reports OK when it should not, (d) quadratic or whole-file-per-call performance.
2. Each proven defect is one added file `tests/rv1110_<name>.py` that asserts the correct behaviour (so it exits 1 on this head) and holds at least one passing `test_control_*`; nothing under `src/` or any existing test is edited, nothing is fixed, committed or pushed.
3. The deliverable is this file: a findings table, suspected-unconfirmed items, measured performance, documentation claims the code does not implement, and what was checked and found correct. R1/R2 findings (praxa broker, token replay, stale-handle file mode, malformed-tail gate, reader lock) are not repeated.

## Assumptions not stated in the task

- "Correct behaviour" is taken from the repository's own statements (README.md, SECURITY.md, docs/SECURITY_ASSESSMENT_SCOPE.md, docstrings) and, where they are silent, from agreement between the two implementations: a ledger one implementation writes or accepts and the other rejects is a defect in one of them.
- The threat model is the one R1/R2 used: SECURITY.md "Scope" plus docs/SECURITY_ASSESSMENT_SCOPE.md (a local party with raw write access to the file; a crash at any point of an append). A whole-chain rewrite by a party without the signing key on an unsigned ledger is documented as out of scope and is not reported.
- A crash is simulated by writing the bytes a dying writer would leave (a prefix of a record, a record without its newline) into a `tmp_path` file; no process is killed and no fault injection into the kernel is used.
- The Rust side cannot be built or run until `BATTERY_DONE` exists. Until then Rust behaviour is established by reading source or by a pre-built `argus_verify` binary whose source commit is recorded here; such findings are marked unconfirmed until re-run with cargo.
- Performance is measured on a loaded box pinned to one core at nice 19, so only growth rates (ratio between sizes) are reported as evidence, not absolute times.
- Inputs stay under 1 MB and go through the library's public API or through a ledger file on disk, which is the verifier's input.

How those assumptions turned out: no pre-built `argus_verify` binary was used for any finding; see "What the Rust results rest on" below.

Load marker, as observed: I read `BATTERY_DONE` with a modification time of 21:59:14 UTC and ran cargo only after that (`cargo test` from 22:01:29, the two `rsprobe` builds at 22:04 and 22:06, the whole Python suite once at 22:07; times are the file times of `scratch-argus/cargo_test.out`, the `rsprobe` binaries and `full_suite.out`). At 22:21:14 UTC the marker was absent again (its directory changed at 22:21:07). From then on nothing was built and the whole suite was not run again; the later runs are single test files and the already built binaries, pinned with `taskset -c 19 nice -n 19`. The 21:59:14 reading cannot be re-checked now that the file is gone.

### Notes on the findings

- R3-2 and R3-3 share one cause (no nesting limit in `validate_payload`); they are two files because the effects differ (permanent self-inflicted outage vs. verdict depending on the verifier). Measured boundaries with `{"d": [[...1...]]}`: 126 lists agree, 127-198 split, 199+ brick.
- R3-4, R3-9 and R3-19 are three sides of the append path. R3-4: the writer is still alive and holds the lock when the write fails, and leaves the fragment. R3-9: after a crash nobody can clean up, and the next writer refuses for ever. R3-19: the write completed, the sync failed, the caller is told "failed" and the record stays. One fix site each: the error path of `append()`, the tail gate, the error path again.
- Relation to earlier rounds: R1 item 6 (`tests/review1_append_extends_malformed_tail.py`) was that `append()` extended a malformed tail; R2 section 5 records the fix (the tail parse gate at ledger.py:277-283). R3-2, R3-4 and R3-9 are what that gate does with tails the writer itself, or a crash, produced. R3-11's last row is a case the gate still lets through.
- R3-9 is partly a policy question. The test asserts that the writer recovers and keeps every acknowledged record. If refusing is intended, the defect is that there is no supported way out and docs/SECURITY_ASSESSMENT_SCOPE.md:53 calls the self-bricking writer resolved.
- R3-5: the library's own readers return the committed values (last key wins). The exposure is to anything else that reads the JSON Lines file, and to the stated property at docs/SECURITY_ASSESSMENT_SCOPE.md:46.
- R3-17 and R3-20 need a third writer or someone with write access to the file; neither Argus writer produces those records. They are listed because the two verifiers give opposite verdicts on them.
- R3-13 and R3-17: stored floats in any spelling other than Python's (`1.50`, `1e2`, `1E2`) also split the verifiers (scratch `probe2.out`, `probe3.out`: the Python verifier re-serialises the parsed number, the Rust verifier hashes the stored text). That is the float limitation the changelog documents and neither writer emits floats now, so it is not listed separately. R3-17 is the one integer token with the same behaviour.
- R3-15 and R3-16 concern `argus_ledger.proofweave`, which README.md marks experimental. R3-16 is outside the round-3 cut and is listed because it was found while measuring R3-15.

## Suspected, unconfirmed

Code reasoning only; none of these has a test.

1. `argus-verify` takes no file lock (no `flock` anywhere in `src/bin/argus_verify.rs`; it opens the file at :67 and reads to EOF), while `FileLedger::verify_chain_with` takes `LOCK_SH` (src/file_ledger.rs:596) and the Python reader snapshots the size under `LOCK_SH` (src/argus_ledger/ledger.py:132-136). Run while a writer is between two `write` calls, the CLI can read a partial last line and exit 1 ("malformed record"): a false integrity alarm. The on-disk state it would see is the R3-9 fixture, for which the CLI does exit 1; the race itself was not reproduced.
2. Rust `FileLedger::append` after a failed `write_all` leaves the partial line, and after a failed `sync_data` leaves the whole record while returning `Err` (src/file_ledger.rs:334-338, 458-462). Same reasoning as R3-4 and R3-19; no fault was injected into the Rust writer.
3. Rust `FileLedger::new` creates the parent directory and the file (src/file_ledger.rs:63-71) and never syncs the directory. Same reasoning as R3-12.
4. `_snapshot_lines` relies on "that size ends where the last complete append ended" (src/argus_ledger/ledger.py:121-122). After R3-4 that is false: the size can end inside a fragment. The visible consequence is already R3-4; no further effect was found.
5. `append()` with a lone surrogate in the payload or in `event_id` raises a bare `UnicodeEncodeError` (the file is left unchanged, scratch `probe6.out`) instead of `PayloadError`. Callers that catch the package's own error types miss it. Not written up as a finding: nothing is corrupted and the input is refused.
6. A garbage `signature` value on a record of an unsigned ledger is ignored by both verifiers when no key is given (scratch `probe4.out`, `shape/sig_garbage_unsigned`). Consistent with SECURITY.md:33 (no key, internal consistency only), noted because the R3-5 class (bytes in a record that verification does not cover) also exists there.

## Performance

Scripts: `scratch-argus/perf1.py` (output `perf1.out`), `scratch-argus/perf2.py` (`perf2.out`), `scratch-argus/probe8.py` (`probe8.out`), `scratch-argus/rsprobe` mode `bench` (`perf_rust.out`). One core (`taskset -c 19`, nice 19), `os.fsync` replaced by a no-op in the Python scripts so the numbers show the library's work and not the disk. Records carry a 100-character payload; the largest file is 15 MB.

Python `AppendOnlyLedger`:

| records | file | append | bytes read per append | head() | len() | get_event(last) | verify (Python) | verify (native) |
|---|---|---|---|---|---|---|---|---|
| 1,000 | 0.5 MB | 89 us | 65,537 | 28 us | 29 us | 4.2 ms | 21 ms | 2 ms |
| 4,000 | 1.9 MB | 90 us | 65,537 | 29 us | 29 us | 17.2 ms | 81 ms | 9 ms |
| 16,000 | 7.5 MB | 89 us | 65,537 | 29 us | 29 us | 70.2 ms | 326 ms | 35 ms |
| 32,000 | 15 MB | 90 us | 65,537 | 29 us | 29 us | 141.2 ms | 852 ms | 68 ms |

- `append()`, `head()` and `len()` do not grow with the file: one 64 KiB tail read per call. Not quadratic, no whole-file read per append.
- `verify_chain()` is linear on both paths: 20.3 to 20.5 us per record for the Python loop at 4,000 to 32,000 records (`perf2.out`, best of three), about 2 us per record natively. Memory held by the Python loop levels off near 1.2 MB between 16,000 and 32,000 records (`perf2.out`); it does not hold the file.
- `get_event(n)` is a scan from the start of the file on every call (4.4 us per record). One call is linear; a caller that fetches events one by one pays quadratic time. `iter_events(start=...)` scans the same way. Reported as measured behaviour, not as a finding: no document promises an index for the Python side.
- The next append after a large record reads that record back: 900 kB previous record, 900 kB read in 16 calls, 2.2 ms. Linear in the size of the last record only.
- Error path: a failed `append()` or `head()` on an unparsable tail re-reads the file to count lines (1.3 ms at 4,000 records, 10.3 ms at 32,000). Linear, and only on the error path.

Rust `FileLedger` (release build, real `sync_data`):

| records | append | head() | get_event(last), same handle | get_event(last), new handle | verify |
|---|---|---|---|---|---|
| 1,000 | 1,217 us | 13 us | 6 us | 1.5 ms | 4.3 ms |
| 4,000 | 873 us | 14 us | 7 us | 3.6 ms | 5.0 ms |
| 16,000 | 884 us | 14 us | 7 us | 14.0 ms | 21.3 ms |

- Append and head are constant. Verify grows 4.3 times from 4,000 to 16,000 records (linear); the 1,000-record figure is dominated by a fixed cost. `get_event` is fast only through the in-process index that appends in the same process fill: a handle opened on an existing file scans from offset 0 (14 ms at 16,000 records, growing linearly).

`MerkleMountainRange.append()` (finding R3-15): 1,000 appends 0.33 s, 2,000 appends 1.29 s, 4,000 appends 5.3 s, 8,000 appends 21.0 s. Time quadruples when the leaf count doubles. Counted in the test instead of timed: 512 appends take 129,535 SHA-256 calls (253 per append).

Concurrency (`scratch-argus/conc1.py`, `conc1.out`): three writer processes of 300 appends each plus one reader process that ran `verify_chain()` 300 times (both verifiers) and `head()` 150 times against the growing file. Final chain valid with 901 records, 300 from each writer, and no reader verdict was invalid.

## Checked and found correct

Verified by running the code (scratch probes named in brackets), without finding a defect:

- Structural tampering, both verifiers, same verdict and same `first_broken_sequence` [`probe9.out`]: dropped middle record (3), duplicated middle record (4), duplicated tail (6), two records swapped (2), reversed file (1), dropped first record (1), a file holding only record 3 (1), chains built with valid hashes that start at sequence 2, at sequence 0, or with a non-genesis `prev_hash` (1), a sequence gap 1,3 (2), a repeated sequence 1,1 (2), a regressing timestamp and an equal timestamp (2).
- Tail truncation and the empty file pass without an anchor, as documented (SECURITY.md:33, src/argus_ledger/ledger.py:487-488), and fail with the head anchor at the anchor's sequence on both verifiers. An anchor at sequence 3 passes a chain truncated to 4 records and fails one truncated to 1 or 0 [`probe9.out`].
- A file with no trailing newline, blank lines between records, a whitespace-only file and CRLF line endings: same verdict from both verifiers, and from `head()`/`append()` [`probe9.out`, `probe7.out`]. A complete last record with no newline is kept and the next append adds the separator, in Python (ledger.py:333) and in the Rust `FileLedger` [`rust_confirm.out`]. A UTF-8 BOM is rejected at record 1 by both.
- Canonical JSON for what the writers can emit, Python-written and verified by both [`probe6.out`]: key order with a BMP private-use key against an astral key (code-point order on both sides; the Rust writer accepts the same order), NFC and NFD forms of one key kept distinct, NUL, DEL, empty and space keys, U+2028/U+2029/U+0085/CR/LF/0x1C inside string values, quote/backslash/control escapes, integers at +/-(2**53 - 1), nested booleans/null/empty containers, noncharacters, `True` next to `1`.
- Canonicalisation of non-canonical stored payloads agrees for: `\u0061\/` escapes, duplicate keys inside the payload (last wins on both), integers above 2**64 [`probe3.out`]. (The same probe shows the two canonicalisers also agree on non-object payload text; the verifiers do not, which is R3-20.)
- Rust writer gates [`rust_confirm.out`]: refuses `-0`, floats, duplicate keys, unsorted keys and a payload nested 127 levels; a ledger it wrote verifies under the Python verifier and `argus-verify`.
- Record shape: `hash_version` null or `true`, trailing garbage after a record, two records on one line, form feed or U+2028 inside a record's whitespace are rejected by both verifiers [`probe4.out`].
- Timestamps, same verdict on both sides [`probe2.out`]: lower-case `t`, space separator, comma fraction, dot without fraction, leading `+` on the integer form, u64 max and u64 max + 1, year 9999, Feb 31, second 60, no offset, offset 14:59.
- Concurrency: three writer processes and a verifying reader on one file, no lost or interleaved record and no false verdict [`conc1.out`]. The reader snapshots the size under `LOCK_SH` and reads without a lock (ledger.py:118-146).
- Anchors: sequence 0 and negative values are refused by `ChainAnchor`; an upper-case anchor hash fails on both verifiers; `legacy_timestamps_before` of 0 or a negative value raises ValueError on both paths [`probe8.out`].
- Signed ledgers: a changed payload value is detected at its record under HMAC and Ed25519 (the controls of `tests/rv1110_signed_record_malleable.py`); a wrong Ed25519 key fails at sequence 1.
- Performance of `append()`, `head()`, `len()` and `verify_chain()`: constant, constant, constant and linear (section above).
- Existing suites on this head, after `BATTERY_DONE`: `cargo test --no-fail-fast` exit 0 (34 unit tests passed and 1 ignored, 6 CLI tests, 1 doc test; `scratch-argus/cargo_test.out`); `pytest tests` exit 0 (99 passed, 4 skipped, 80 subtests passed; `scratch-argus/full_suite.out`).

## Not checked

- Real power loss or kernel-level fault injection: every crash state is simulated by writing the bytes a dying writer would leave.
- A Python writer and a Rust writer appending to one file at the same time (both use `flock(2)` by reading; not run together).
- Non-POSIX platforms, network filesystems, `InMemoryLedger`, the praxa broker (R1/R2 scope), `proofweave` beyond `MerkleMountainRange`.
- The PyO3 binding rebuilt from this head (see "What the Rust results rest on").
